# Changelog

This log groups changes by the finding/task each cluster of edits addresses, rather than by commit or file, so the *why* behind each group of changes stays clear without re-reading every diff.

## Group A — Online: genuine F_coin realization for r_k / ε_sigma / ε'_batch / ρ

**Files:** `crates/online/src/vip.rs`, `crates/online/src/compute.rs`, `crates/online/src/compute_parallel.rs`, `crates/online/src/compute_batch.rs`, `crates/offline/src/rss_share.rs`

**What was wrong.** In `vip_parallel`, the γ-round Fiat-Shamir sequence `r_ks` was derived by appending the *same constant label* (`b"r_k"`) every loop iteration and calling `Transcript::challenge()` — which does not mutate the hasher — so every value in the sequence came out bit-identical, not merely unbound from committed prover data. Separately, the σ-update coefficients (`ε_2..ε_γ`, inside `vip_single`) and the Σ-batch coefficients (`ε'_i`, in `vip_parallel`) were sampled from `rand::thread_rng()` — private, per-call randomness that a corrupt party could effectively choose, and that wasn't even shared across the `n` parallel `Π_VIP` instances the way the protocol requires.

**Why it mattered.** A malicious prover could predict `r_k`/`ρ` in advance (they were public/constant) and adaptively choose its `q`-values to pass the `d_i = a_i^(1)·b_i^(1)` and `σ_i = 0` checks while still embedding an arbitrary error — the core soundness property Π_VIP exists to provide.

**Why the fix isn't "add more Fiat-Shamir binding".** The obvious-looking fix (bind `r_k`/`ρ` into a transcript with more committed data, as an earlier review pass suggested) is not what the paper allows here. Appendix L of the paper states explicitly that "the Fiat–Shamir transform is not applicable to the batched VIP protocol (Protocol 5) and our dVOPRF protocol (Protocol 6)", and that "FCoin at the last step in Π_VIP must be called" as a genuine coin toss. Protocol 5 also requires `r_k`/`ε_k` to be identical across all `n` parallel `Π_VIP` instances for a given round — something a per-instance Fiat-Shamir derivation can't provide anyway.

**The fix.** Added a `coin_toss` helper in `vip.rs` that realizes a genuine, un-biasable F_coin: every party independently derives its own PRF-keyed RSS share of the same secret value (no communication needed — deterministic given a shared counter and `pre_shared`), then the value is opened via `ReplicatedSharing::reconstruct_from_party_shares`. This exactly mirrors the `generate_double_sharing` pattern already used correctly in this file for the `(a₀, b₀)` output-randomization values — it just wasn't applied to `r_k`/`ε`/`ρ`. All of `vip_parallel`'s F_coin calls (`r_k` per round, `ε_2.. ε_γ`, `ε'_i`, `ρ`) now go through `coin_toss`, drawn up front (a genuine coin toss has no ordering dependency on committed data, unlike Fiat-Shamir, so there's no need to interleave rounds). `vip_single` gained one new parameter, `eps_sigma: &[Fp]`, for the caller-supplied shared σ-update coefficients. The now-unused `Transcript` parameter was removed from `vip_parallel`'s signature; call sites in `compute.rs`, `compute_parallel.rs`, and `compute_batch.rs` were updated accordingly — `compute_batch.rs`'s own, separate, already-correct commit-then-hash mechanism for batching `m` client inputs (Protocol 6's `ε_j`) is unrelated and was left unchanged.

**Round-count follow-up.** All of these draws are independent of each other (unlike a Fiat-Shamir sequence), so they don't need one network round each — they can all be requested and opened together. Added `charge_f_coin_batch` (`crates/offline/src/rss_share.rs`) so `vip_parallel` charges the *entire* `r_k`/`ε_sigma`/`ε'`/`ρ` draw as a single batched round instead of one round per value, matching Appendix M's own round accounting ("`FCoin` to generate `ε'_1,...,ε'_n` can be simultaneously called with `FCoin` at the last step of the single VIP protocol"). Added `vip_parallel_round_count_independent_of_gamma` as a regression test: `comm.rounds` must not grow with γ = ⌈log L⌉, only the byte count should.

While verifying this against the bench binary (Section 2, VIP-ComputeBatch, full `(n,t) ∈ {(3,1),(5,2),(7,3),(9,4)}` × `m ∈ {1,100}` sweep), found and fixed one more subtle over-count in the same helper: `SimulatedNetwork` already counts "1 round used" for any activity at all (`num_rounds() = current_round + 1`), so `charge_f_coin_batch`'s original trailing `net.next_round()` double-counted the batch's own round whenever it was the only activity on a fresh network (which is exactly how `vip_parallel` uses it) — costing 2 rounds instead of 1. Moved the `next_round()` call into `charge_f_coin` itself (so its two existing callers in `dzkp.rs`, and the exact-round-count test `compute_boyle_batch_round_topology` that pins their combined total, keep their byte-for-byte prior behavior) and left `charge_f_coin_batch` to only charge bytes at the network's current round. Confirmed via the same bench sweep: VIP-ComputeBatch's round count dropped from 8 to 7 and stayed exactly flat across every `(n,t,m)` combination tested, with byte counts and timings unchanged (pure round-bookkeeping, zero computational impact) — the residual difference from the paper's claimed constant 9 rounds (Table 2, "Our Π^m_dVOPRF") is not from this finding; it traces to other round-accounting conventions already present in the bench harness before this session (client-input distribution, commit-then-hash, VSS-share, RSS.Mul, and RSS.Open charging), which were out of scope here.

## Group B — Online: compute_boyle.rs must return Abort, not panic

**Files:** `crates/online/src/compute_boyle.rs`, `crates/bench/src/main.rs`

**What was wrong.** `compute_boyle_single`/`compute_boyle_batch` called `assert_eq!(verdict, DzkpResult::Accept, ...)` after running the DZKP — a real Fvrfy failure (`DzkpResult::Abort`) would panic the process instead of being reported as a controlled verdict.

**Why it mattered.** The task's checklist requires "reject-for-everyone, no crash" semantics for a real ZKP failure — a process crash is a denial-of-service vector and is a materially worse failure mode than a clean abort.

**The fix.** Removed both `assert_eq!` panics; the functions now return `BoyleProof`/`BoyleBatchProof` with whatever verdict `dzkp_compute_batch` actually produced, mirroring the mutable-verdict-accumulator pattern already used correctly in `approach_iii.rs`. `client_deliver_boyle` in `bench/src/main.rs` was updated to check `proof.verdict` before delivering `open_shares` to the client — on `Abort` it now sends only the verdict-announcement bytes and returns no outputs, instead of unconditionally treating (possibly meaningless) shares as valid.

## Group D — Offline: VitH secret GGM seed + two-level Merkle input binding

**Files:** `crates/offline/src/zkp_vith.rs`, `crates/offline/src/approach_iii.rs`

**What was wrong (two findings, one mechanism).** The GGM tree's root seed was derived via `transcript.challenge(...)` — a pure function of public data (the witness commitment, δ, and the repetition index) — instead of the prover's own secret randomness. Anyone, including the verifier, could recompute the entire GGM tree, including the "hidden" leaf, directly inverting the masked witness to recover the real witness (breaking zero-knowledge) and forging proofs for false witnesses (breaking soundness), since the only check on the free values `(Ã₀, Ã₁)` was a single linear equation solvable given a public correlation. Separately, the paper's headline contribution — a two-level GGM/Merkle commitment binding the proof to each verifier's own locally-held `(m_T, a_T)` shares — was entirely absent: `VitHProof` had no commitment-root field, `vith_verify`'s `_local_shares` parameter was unused dead code, and `approach_iii.rs` fed it an always-empty map plus a zero-filled placeholder for the "authentication path" data.

**The fix**, following the paper's Protocols 15-16 (Section 4.2.2) exactly, reusing primitives already in the codebase (`MerkleTree`, `hash_commitment`, `Transcript`) rather than inventing new crypto machinery:
- The GGM root seed (`sd`) is now generated via `rand::thread_rng()` — the prover's own secret randomness, never derived from the transcript.
- For each of the τ GGM leaves, a sub-Merkle-tree is built over that leaf's expanded share vector (`leaf_commitment_tree`), giving a per-leaf root `h_i`; an outer Merkle tree over `{h_i}` gives the commitment root `rt`. `rt` is committed into the transcript *before* the masked witness and before the hidden index `Δ` is drawn (previously nothing meaningful was committed before `Δ`).
- `vith_verify` now checks that `rt` genuinely commits to the real leaf structure: it recomputes `h_i` for every non-hidden leaf (whose seed it can now reconstruct from the existing GGM co-path) and takes the prover-supplied `h_Δ` for the hidden leaf, then verifies the resulting Merkle root matches `rt`.
- `vith_verify`'s `local_shares` parameter is now used and retyped to `BTreeMap<usize, Fp>` (witness position → locally-known value). For every position present, it recovers the hidden leaf's committed share at that position from the masked witness and the verifier's own local value, and checks it against `h_Δ` via a sub-tree Merkle authentication path — this is the actual "dual-share consistency" check: a dealer whose broadcast proof disagrees with what a verifier already knows locally is now caught, independent of the QuickSilver check.
- `approach_iii.rs` no longer passes an empty map / zero-filled bytes: it builds the real `local_shares` map for one simulated verifier by re-deriving `(m_T, a_T)` from that verifier's own PRF-keyed view (reusing the dealer's own derivation logic), and sends the genuine sub-tree authentication path bytes for those positions instead of a placeholder.

## Group E — Shared: hash_field_elements length-framing

**Files:** `crates/crypto-primitives/src/hash.rs`

**What was wrong.** `hash_field_elements` concatenated each field element's unpadded, variable-length big-endian bytes with no length prefix or delimiter, so two structurally different element vectors could hash identically (e.g. `[Fp(1), Fp(2)]` and `[Fp(0x0102)]` both concatenate to `01 02`). `Transcript::append_field_element` already handled this correctly elsewhere in the codebase with a 4-byte length prefix per element — this function just hadn't been brought in line.

**The fix.** Added the same 4-byte big-endian length prefix per element. Confirmed safe across all 9 call sites (each calls the function identically on both the producing and verifying side within the same protocol; no test hardcodes raw digest bytes; the two cross-file byte-identity requirements — `compute_batch.rs` ↔ `vip.rs` — both go through this same function, so they stay mutually consistent automatically).

## Group F — Offline: Ligero verifier panic + query-position dedup

**Files:** `crates/offline/src/zkp_ligero.rs`

**What was wrong.** `ligero_verify` validated the lengths of four of its proof vectors before use, but not `opened_columns_j`/`opened_columns_next`/`merkle_paths_j`/`merkle_paths_next` — a malformed or adversarial proof with fewer entries than `query_positions` would panic with an out-of-bounds index instead of being cleanly rejected (an availability/DoS-class bug). Separately, the query-position sampling loop (in both `ligero_prove` and `ligero_verify`) silently dropped a duplicate sampled position instead of resampling, so `query_positions` could end up shorter than `params.num_queries` — slightly under-sampling below the nominal soundness parameter.

**The fix.** Added the missing length checks before the indexing loop, returning `false` on mismatch. Changed both sampling loops (kept structurally identical to each other, as required for prove/verify to derive the same positions) to resample on a duplicate instead of dropping it, so `query_positions.len()` always equals exactly `params.num_queries`.

## Group G — Offline: two-level leaf hash formula doc note

**Files:** `crates/offline/src/zkp_ligero.rs` (doc comment only)

Added a note on `two_level_leaf` that it computes `H(H(share)‖H(priv))` rather than the paper's literal `H(share‖H(priv))` — an intentional, sound deviation (a verifier holding only share values can still independently recompute `share_hash` and check it against the leaf without seeing the private rows, confirmed by `ligero_verify_partial_opening` and its test).

## Group I — Online: implement Π_Input, verifiable client input sharing

**Files:** `crates/online/src/input.rs` (new), `crates/online/src/lib.rs`, `crates/online/src/compute_batch.rs`, `crates/secret-sharing/src/lib.rs`, `crates/offline/src/rss_share.rs`, `crates/bench/src/main.rs`

**What was wrong.** `share_add_and_extract_pairs` (used by `compute`, `compute_parallel`, and `compute_batch`) treats the client as an ad-hoc local dealer: it just calls `vdoprf_ss::share(x, ...)` directly, with no consistency check at all. The paper (Appendix E.1) calls this out explicitly: "a malicious client can send mismatched copies of a replicated component `[x]_ℓ` to two servers that both hold it, and nothing detects the inconsistency." The paper's own text also flags several of its *own* tables as stale — `[Implementation rework pending: these numbers predate ΠInput...]` — confirming `Π_Input` (Protocol 9) is a real, load-bearing part of the paper's design this codebase never implemented.

**The fix.** Implemented `Π_Input` for real (verifiable, value-producing logic, not just a comm-cost estimate), in a new `crates/online/src/input.rs` module:
- `client_input_share` — steps 1-3 (mask-and-open with an abort-checked `ψ_i` hash) and step 5 (each server locally derives `[x^(j)]_i = u^(j) − [r^(j)]_i`). The `P:[N]→[n]` designated-sender assignment reuses the existing `covering_policy` (already used for this exact role by `generate_double_sharing`/`rss_to_additive`); the pre-computed `[r^(j)]` reuses `generate_rss_random` (the same PRF-derived, no-communication primitive this session's `vip.rs` `coin_toss` fix already relies on).
- `client_input_share_standalone` — the *full* protocol at the paper's stated standalone 3-round cost, composing the above with `verify_echo_standalone` (step 4's echo, checked as its own round).
- Added `RssShare::local_sub_public` (public-scalar subtraction on an RSS share) for step 5. First attempt reused the "one designated party absorbs it" pattern from `deg_mul`/`rss_to_additive` — which is correct for RSS→*additive* conversion, but **wrong** for producing a fresh, still-valid RSS share: it broke the replication invariant (every holder of a subset must keep reporting the *same* value for it) for exactly the canonical subset, silently corrupting all downstream RSS operations for every non-absorbing party. Fixed to have *every* holder of the canonical subset apply the identical adjustment — caught by `compute_batch_with_verified_input_matches_compute_batch`, which failed loudly (reconstructed value mismatch) the first time it ran; the isolated `input.rs`-level test hadn't caught it because it only fed the output straight to `reconstruct_from_party_shares`, never through further RSS operations like `local_add`/`cross_multiply`.
- Added `charge_input_client_facing`/`charge_input_echo_standalone` to `rss_share.rs` for `Π_Input`'s real communication cost (the existing `charge_client_rss_share` approximation is left untouched — nothing here removes it).

**Per confirmed scope, only the folded (2-round) variant is wired into anything benchmarked**; the full standalone (3-round) variant is implemented and covered by its own tests but is dead code from the benchmark's perspective. `compute.rs`/`compute_parallel.rs` are untouched. `compute_batch` gets **two separate functions**, not a flag:
- `compute_batch` — unchanged, exactly as before (unverified input) — kept as the "without input verification" comparison baseline.
- `compute_batch_with_verified_input` — new; identical downstream logic, but client input goes through `Π_Input` first. Its own return type, `VerifiedInputResult { Accept(OnlineResult), Abort(CommStats) }`, is deliberately separate from `OnlineResult`/`OnlineProof` so the addition is fully additive.

**The round-merge, and a bug it caught.** Step 4's echo is folded into `compute_batch`'s existing Step-2 commit-then-hash round rather than costing a separate round. First attempt combined `χ_i` into the *same* hash used to derive `ε_k` (via `hash_pair`) — which silently broke the existing, unmodified client verifier (`client_verify_dvoprf`), since it independently re-derives `ε_k` from a plain `H(tilde_v[i])` it has no way to know was folded. Caught immediately by a bench smoke run (`client verify must Accept on honest execution` failing). Fixed by keeping the `ε_k`-deriving hash byte-identical to the unverified path and instead appending `χ_i`'s bytes to the *same broadcast message* — same round, `+32` bytes per server, rather than combining into one digest. Also added `client_verify_dvoprf` (not just `client_verify_vip_parallel`) to the honest-path test, since that's specifically the check that had caught this.

**Bench:** added a `VIP-CB+VerifiedInput` row in Section 2 alongside the existing `VIP-ComputeBatch` row — this is the actual "with vs. without input verification" comparison surface. Confirmed via a scoped run: rounds go from 7 to 8 (not the `+2` you'd get from `Π_Input`'s 2 real client-facing rounds alone) — because the *existing* baseline's own input charge (`charge_client_rss_share`, used only by the unverified row) under-counts: it charges two logically-sequential sub-steps (servers→ client, then client→Q) on a single network without ever calling `next_round()`, landing on 1 charged round for what should be 2. That's a pre-existing accounting looseness in code this pass didn't touch, not a bug in the new accounting — `Π_Input`'s own 2 rounds (via two separately merged networks) are the more careful count. Bytes and timings otherwise move exactly as expected (S↔C bytes increase with the real `ψ_i`/`u` traffic now charged; timings track the unverified row within noise, since the underlying VIP computation is identical).

## Group J — Bench: standalone/parameterized experiment interfaces + Legendre-dOPRF baseline wrapper

**Files:** `crates/bench/src/main.rs`, `crates/bench/src/avg.rs`, `run_bench.sh`, `run_legendre_baseline.sh` (new)

**What was missing.** The bench crate only supported "run everything, exactly as hardcoded" (`cargo run --release -p vdoprf-bench`, or `./run_bench.sh`) — there was no way to run a single experiment, no CLI parameter handling at all (zero `std::env::args()`/`clap` usage anywhere in `crates/bench/src/`), and `crates/bench/src/avg.rs`'s test module had two compile errors (both drift against the real `CommStats`/`bench_avg_split` shapes: `constant_stats` was missing the `client_bytes`/`client_messages` fields; `bench_avg_split_constant` called `bench_avg_split` with a 3-tuple closure against a 2-tuple-expecting signature). Separately, a fourth baseline — the external Legendre-dOPRF C/network implementation (Kaluđerović et al., ESORICS'25), vendored as the `d-OPRF` git submodule — was only ever *documented* (a stale comment in `main.rs` pointed at a `bench_e2e.py`/`build_all.sh` that don't exist; the real entry points are `go128.sh`/`go256.sh`) and never actually runnable alongside the Rust harness.

**The fix.**
- Fixed both `avg.rs` compile errors (see above); `cargo test -p vdoprf-bench` now compiles and passes (this crate has no `[lib]` target, only `[[bin]]` — its tests run via `cargo test -p vdoprf-bench`, not `--lib`).
- Added a hand-rolled `std::env::args()` CLI to `crates/bench/src/main.rs` (no new dependency, matching the crate's existing style): an `Experiment` enum (`all` / `offline` / `online` / `e2e` / `our-protocol` / `our-protocol-verified-input` / `naive-boyle-aly`), `--n N --t T` (both-or-neither) to override the (n,t) sweep to a single pair, and `--m M1,M2,...` to override the m sweep — all defaulting to today's values, so `Experiment::All` with no flags reproduces the historical unconditional three-section run byte-for-byte (confirmed: rounds/bytes for `our-protocol` vs `our-protocol-verified-input` differ only in the expected small `Π_Input`-cost increment — see Group I — with `I: AlyGen + BoyleBatch` identical between them, as it must be).
- Added `OnlineVariant::VipVerifiedInput` (alongside the existing `Vip`/`Boyle`) so `run_one_e2e_iter`/`run_e2e_set` can drive the e2e composition through `compute_batch_with_verified_input` instead of `compute_batch` — skipping the separate `client_to_servers_input` charge for this variant specifically, since `Π_Input`'s real cost is already inside its own `comm` (mirroring Section 2's existing `VIP-CB+VerifiedInput` reasoning). `our-protocol`/`our-protocol-verified-input` are the same `run_e2e_set` sweep (offline II/III-a/III-b + the fixed Aly+Boyle baseline row), differing only in this one parameter.
- `naive-boyle-aly` maps directly to the existing, already-fully-functional `e2e_aly_boyle` (previously orphaned dead code, reachable only via a commented-out block) — no changes to that function itself.
- New `run_legendre_baseline.sh` (repo root) drives the Legendre-dOPRF baseline **without ever modifying the `d-OPRF` submodule's own tracked files**: it sed-patches `dOPRF.h`'s `CONST_T`/`CONST_N`/`ADVERSARY` exactly as `go128.sh`/`go256.sh` do, rebuilds only the client/server pair needed, then drives them itself — fixing a real bug in the upstream scripts' own process handling (`go128.sh`'s `CLIENT_PID=$!; wait $CLIENT_PID` is a no-op: `$!` is captured *after* the client, which isn't backgrounded, has already run to completion in the foreground; this script instead explicitly tracks the *server* PIDs, which are the processes that actually need lifecycle management). Always restores the submodule afterward via `git checkout` + `git clean -fd` scoped to the submodule's subdirectory (undoing the `dOPRF.h` patch, the tracked-binary rebuild diff, and untracked `server_offline_*.txt` cruft the servers write into their cwd), with pre- and post-run cleanup of any stray server processes. Only exposes the `(t,n)` pairs the vendored C macros/upstream scripts actually support (`128`: `(1,4)`, `(2,7)`; `256`: `(1,4)`) rather than pretending free parameterization. Supports `--m 1|100|1,100`: since the C client has no internal query loop *and* the server exits after handling its one client connection (confirmed by reading `network-version/{client,server}.c`'s `main()` — there is no loop around `accept()`), `m=100` restarts the full server set and re-runs the client 100 times in sequence, summing the parsed `Total time required dealing messages`/`Total communication size` — labelled explicitly in the output (`"100 (100 sequential runs, summed)"`) since this is a materially different cost model from the Rust harness's own batched `m`. Verified: `--level 128 --tn 1,4 --m 1` and a full `--level 128 --tn 1,4 --m 100` (100 sequential real server-restart-and-query cycles, ~3.5 min) both run and leave `git status --porcelain` on the submodule empty and no `server256`/`server512` processes behind, including after a mid-run kill (the `trap ... EXIT` cleanup fires on SIGTERM too); the `--m 100` totals scaled exactly linearly (comm bytes: 100×) confirming the summation is correct.
  - **Noted, not fixed** (out of scope — it's in the vendored C, and reproduces the same on an unmodified submodule checkout): the client's self-reported "Total time required dealing messages" subtracts a bandwidth-correction term assuming real independent network links to each server; run over loopback (as this wrapper necessarily does, all servers + client on one machine) that correction can exceed the tiny real loopback latency and produce a negative figure for larger `(t,n)` (e.g. `(2,7)`) — flagged directly in the script's own printed output rather than silently reported. Communication-size figures are unaffected.
- Rewrote `run_bench.sh` as a single dispatcher: no arguments runs everything (Rust `all` + the Legendre baseline across every level, `m ∈ {1,100}` — per confirmed scope, the external baseline is included in the "run everything" path, not opt-in-only); a named Rust experiment forwards to `cargo run --release -p vdoprf-bench -- <name> [flags]`; `legendre-dOPRF [flags]` forwards to `./run_legendre_baseline.sh`.

## Group K — Bench: verified-input Boyle+AlyGen, merged e2e table, dOPRF in `run_bench.sh`

**Files:** `crates/online/src/compute_boyle.rs`, `crates/bench/src/main.rs`, `run_bench.sh`

**What was wrong.** Group I gave the VIP online path a Π_Input-verified variant, but the Boyle/BGIN20 online path (`compute_boyle.rs`) still only ever used the unverified `share()`-as-dealer client input, everywhere it was benchmarked (Section 2's `Boyle-Batch` row and the `naive-boyle-aly` e2e baseline). Separately, following on from user feedback during this pass: **the unverified-input paths must not be wired into any benchmark at all**, for either protocol — a deliberate reversal of Group I's "show both, with vs. without verification" design for VIP specifically. `e2e`'s "run every e2e experiment" output only ever swept one online variant, and `run_bench.sh`'s Legendre-dOPRF section was reachable only via the no-args "run everything" path or its own dedicated `legendre-dOPRF` command, not via `e2e`/`all` directly.

**The fix.**
- Added `compute_boyle_batch_with_verified_input` to `compute_boyle.rs`, mirroring `compute_batch_with_verified_input`'s structure: the shared RSS.Mul + DZKP body was extracted into `compute_boyle_batch_inner` (takes already-obtained per-input, per-party RSS shares of `x`), and both `compute_boyle_batch` (unverified, unchanged) and the new function call into it. Unlike VIP's `compute_batch`, Boyle's RSS.Mul + DZKP pipeline has no pre-existing hash-broadcast round to fold Π_Input's step-4 echo into without touching its round-count-pinned internals (`compute_boyle_batch_round_topology` pins exactly 9 rounds) — so the verified-input path uses the already-implemented, already-tested **standalone 3-round** `client_input_share_standalone` as-is (previously dead code from the benchmark's perspective; now used for real). New `BoyleVerifiedInputResult { Accept(Vec<Fp>, BoyleBatchProof, CommStats), Abort(CommStats) }`, a fresh `BOYLE_INPUT_COUNTER_BASE = 70_000` (confirmed disjoint from every other counter base in the codebase — the double-sharing/RSS-random/zero-additive-sharing generators all draw from one shared per-party keyed-PRF/PRG counter space, so bases must be hand-partitioned globally, not just per-file). 4 new tests mirror `compute_batch.rs`'s verified-input suite: honest correctness (same `c = (x+k)·α^e` regardless of input path), cost comparison, a round-topology pin (9 + 3 = 12, constant in `(n,t,m)`), and an abort-on-forged-server-key test.
- **Per explicit instruction, no unverified-input path is wired into any benchmark any more.** Section 2's `VIP-ComputeBatch` row now calls `compute_batch_with_verified_input` (the separate unverified row from Group I is gone — there's no more "with vs. without verification" comparison surface in this table); its `Boyle-Batch` row now calls `compute_boyle_batch_with_verified_input`. Both drop their separate `client_to_servers_input` charge (Π_Input's cost is already inside the returned `comm`). `OnlineVariant::Vip` (unverified) is removed from the enum entirely; `OnlineVariant::Boyle` (used by both the e2e Aly-Boyle baseline cell and the standalone `naive-boyle-aly` command) now calls the verified-input Boyle function. The `our-protocol` CLI experiment — which existed specifically to benchmark the now-disallowed unverified e2e composition — is **removed**; `our-protocol-verified-input` is the only remaining named "our protocol" e2e experiment. The plain/unverified `compute_batch`/`compute_boyle_batch` functions themselves are untouched and remain fully covered by their own existing unit tests — only their bench wiring is gone. `client_to_servers_input` (the unverified input charge helper in `main.rs`) is now unused by any call site; kept (`#[allow(dead_code)]`) as the reference unverified-cost implementation rather than deleted.
- Since `run_e2e_set` now only ever gets called with `OnlineVariant::VipVerifiedInput` (no more per-variant sweep needed — there being only one benched VIP variant left), `e2e`'s merged table is: 3 offline approaches × the one verified VIP variant + 1 (now verified-input) Aly-Boyle baseline row = 4 rows per `m`. `e2e` and `our-protocol-verified-input` now produce identical tables (confirmed by smoke-testing both at `(n,t,m)=(3,1,1)`: same rounds and bytes, timing differing only by measurement noise) — both names are kept since they serve different discoverability purposes (generic vs. explicit).
- **Expected, intentional output change:** running `online`/`e2e`/`all` with no flags no longer reproduces earlier sessions' exact byte/round counts for the Boyle-Batch row and the Aly-Boyle baseline row (input is now verified everywhere, costing more bytes/rounds — e.g. Section 2's `Boyle-Batch` row at `(3,1,1)` went from 11 to 13 rounds: +3 for Π_Input's standalone cost, −1 because the old separate `client_to_servers_input` charge is gone). This is the deliberate point of this pass, not a regression.
- `run_bench.sh`'s `e2e` and `all` commands now also run `./run_legendre_baseline.sh --level all --m 1,100` as a trailing section (previously only the no-args path did this) — `offline`/`online`/`our-protocol-verified-input`/`naive-boyle-aly` stay Rust-only, since Legendre-dOPRF has no offline/online phase split of its own to compare against, only a full end-to-end query. The no-args path is now simply an alias for `all` with no flags, removing the duplication between the two code paths the script previously had.
- **Follow-up fix found during this pass's own verification:** a full `--level all --m 1,100` run surfaced a real, reproducible failure at `(t,n)=(2,7)`, `m=100` — one of the 100 sequential queries returned `Connection Failed: Connection refused`, which `run_one_query` couldn't parse, and the cell was reported as `FAILED`. Root cause: a transient client/server connection race under rapid repeated server restart (100 restarts of 7 servers in ~8 minutes) — the query itself is stateless and idempotent, so this isn't a protocol bug. Two fixes to `run_legendre_baseline.sh`: (1) the failure-diagnostic log was being deleted *before* the parse-failure check ran, so the printed "see stderr above" pointed at nothing — moved the `rm -f "$log"` to after the check and print the actual client output on failure; (2) added a bounded 3-attempt retry per query in `run_cell`'s loop. Re-ran the exact failing cell (`--level 128 --tn 2,7 --m 100`) after the fix: attempt 97 hit the same `Connection refused`, the retry fired, attempt 2 succeeded, and the full 100-query sum completed correctly (`comm(KB) = 630350.0` = exactly 100 × the single-query 6303.5 KB) — confirmed the fix resolves it rather than masking it.

## Group L — Legendre-dOPRF baseline: genuine 384-bit field infrastructure

**Files:** `d-OPRF` submodule (`Legendre-dOPRF-network/parameters.h`, `.../Makefile`, `.../p384/` (new), `.../network-version/server.c`; submodule commits `6681146`, `8966290`), `run_legendre_baseline.sh`, parent-repo submodule pointer.

**What was wrong.** The vendored Legendre-dOPRF code (Kaluđerović et al., ESORICS'25) only ever shipped `SEC_LEVEL` 0–4 — 64/128/192/256/**512**-bit fields, i.e. `NBYTES_FIELD ∈ {8,16,24,32,64}`. There was no 384-bit field, which is the width the v-dOPRF paper's §Evaluation pins for *both* PRFs (`|p| = 3λ = 384`, so "all benchmarks share the same 𝔽_p"). The originally-submitted Legendre numbers were therefore produced by an **ad-hoc 384-bit configuration that ran on the 512-bit infrastructure**: the element *counts* and the Legendre-symbol batch (`LAMBDA = NBITS_FIELD/2 = 192`) were the true 384-bit values, but each 𝔽_p element was represented and billed at the 512-bit width — 64 bytes, 8×u64, no reduction to a tight 384-bit encoding ("supported, but no wrapping mod 384"). The final aggregation lived in a `.py` script that has since been lost, so this could only be reconstructed after the fact.

**The fix.** Added a real 384-bit field to the submodule (local commits, never pushed upstream):
- `SEC_LEVEL=5` → `NBITS_FIELD=384`, `NBYTES_FIELD=48` (`parameters.h`), a new `p384/generic/arith_generic.c`, and `client384`/`server384` Makefile targets (submodule `6681146`). The modulus is this repo's own Gold-PRF prime `p = 2^384 − 573·2^128 + 1`, so Legendre now runs over *exactly* the same 𝔽_p as the rest of the evaluation, at a matched λ = 128 post-quantum level.
- `run_legendre_baseline.sh` builds and drives `client384`/`server384` (`SEC_LEVEL=5`); `FE = 48` bytes throughout, consistent with the `FE = 48` used for our own protocol's numbers.
- Offline-cost instrumentation in `server.c` (submodule `8966290`) uses `sizeof()` on the actual field structures, so it now reflects the 48-byte width automatically.

**Effect on the reported numbers.** Every 𝔽_p element in the Legendre transcript shrinks 64 → 48 bytes, so **all Legendre communication figures drop to exactly 3/4 (48/64) of the submitted values**; computation and round counts are unchanged (identical element counts, identical `LAMBDA`, same arithmetic). Verified by reconstruction — `submitted_comm ≈ recode_comm × 4/3` at both `(t,n)` points, both `m`:

| point | submitted (KB) | recode (KB) | ratio | 4/3 |
|---|---|---|---|---|
| (4,1) m=1   | 4 425.22      | 3 381.0       | 1.309 | 1.333 |
| (7,2) m=1   | 1 761 188.35  | 1 323 617.9   | 1.331 | 1.333 |
| (4,1) m=100 | 442 522.00    | 338 100.0     | 1.309 | —     |
| (7,2) m=100 | 176 118 835   | 132 361 785.9 | 1.331 | —     |

The `(7,2)` point (communication is almost entirely field elements) lands on 4/3 to within 0.2 %; `(4,1)` sits ~1.8 % below, the difference being fixed-size framing (party indices, subset representations, TCP/serialization headers) that does not scale with element width. As a cross-check, running the *actual* 512-bit binary instead gives `(1,4) m=1 = 5996 KB ≈ recode × (4/3)²` — because in the real code `NBYTES_FIELD` *and* `LAMBDA` both scale with bit-width; the submitted numbers' single 4/3 factor confirms only the per-element byte size was 512-bit, not the batch count.

**Not a regression.** The corrected figures are the faithful instantiation of the `|p| = 384` claim the paper already makes; the submitted communication was conservative by 4/3. No comparison in §Evaluation changes — Legendre still loses by orders of magnitude on communication (≈ 1.3 GB at `t = 2`, ≈ 132 GB at `m = 100`).
